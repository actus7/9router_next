ModelHub — mapa de ponta a ponta

Onde cada dado entra, o que o transforma, e por onde sai. Tudo abaixo foi lido no código em 47ec69b8, não inferido de nome de arquivo. Caminhos são relativos à raiz do repositório.

SEÇÃO 01Como ler este mapa

O sistema tem duas superfícies de entrada completamente distintas, e confundi-las é o erro de leitura mais comum:

Plano de controle

/dashboard/* + /api/*

Onde o operador cria dados: credenciais, combos, chaves, aliases, settings. Autenticado por cookie de sessão JWT.

Plano de dados

/v1/*, /v1beta/*

Onde o dado é consumido: um cliente LLM manda um prompt e recebe resposta. Autenticado por API key da tabela apiKeys.

O elo entre os dois

A tabela providerConnections

O plano de controle a escreve; o plano de dados a lê para escolher com qual conta falar upstream. Nada mais liga os dois planos.

Convenções de notação

  • escreve cria ou altera linhas — é uma entrada de dados.
  • lê apenas consulta.
  • lê+escreve os dois no mesmo fluxo.
  • sai o dado deixa o processo: rede, disco fora do app, serviço externo.
  • blob coluna TEXT com JSON, não colunas relacionais.

O fato estrutural mais importante do schema. Este banco é deliberadamente semi-relacional. Quase toda tabela tem colunas indexáveis (as que aparecem em WHERE) mais uma coluna data TEXT com um blob JSON para o resto.

E não existe nenhuma FOREIGN KEY declarada em src/lib/db/schema.ts, apesar de PRAGMA foreign_keys = ON estar ligado. As relações existem por convenção de código (connectionId, skillId, sessionId, toolId), não por constraint.

Isso responde direto à sua pergunta: o banco não impede nenhuma inconsistência referencial. Quem garante integridade são os repos, e onde eles não garantem, ela não é garantida — ver seção 16.

dataDir.ts tem uma defesa específica de plataforma: no Windows um DATA_DIR em formato Unix (/var/lib/..., vindo de um .env pensado para Docker) é ignorado com aviso em vez de virar um caminho inválido.

Cadeia de drivers — src/lib/db/driver.ts:76

  runtime Bun  :  bun:sqlite          → sql.js
  runtime Node :  better-sqlite3      → node:sqlite (≥22.5) → sql.js

  nenhum funciona → throw "[DB] No SQLite driver available"

Quatro adapters em src/lib/db/adapters/. O primeiro que carrega vence, e o driver escolhido é logado uma vez. better-sqlite3 é pulado no Bun (bindings nativos incompatíveis).

Boot: uma inicialização, uma migração

getAdapter() memoiza tanto a instância quanto a promise de inicialização, então concorrência no primeiro request não dispara duas migrações. initAdapter() chama ensureDirs(), escolhe o driver e só então runMigrationOnce(adapter).

SEÇÃO 04Schema SQL completo — 23 tabelas

Fonte única: src/lib/db/schema.ts, constante TABLES. SCHEMA_VERSION = 8. O runner usa TABLES de forma declarativa: syncSchemaFromTables() adiciona tabelas, colunas e índices faltantes automaticamente a cada boot. Mudanças destrutivas (drop / rename / troca de tipo) exigem um arquivo de migration.

markAccountUnavailable() — que roda a cada falha upstream — deliberadamente não escreve testStatus; ela grava lastError, errorCode, backoffLevel e uma linha em modelAvailability. Uma falha de rate limit não é um teste reprovado. A migration 008 normalizou o vocabulário legado (success→active, expired/unavailable→error).

SEÇÃO 05Migrations, sync declarativo e backup

Dois mecanismos coexistem, e a divisão entre eles é a parte que costuma confundir:

1 · Sync declarativo

syncSchemaFromTables(), migrate.ts:273

Roda a cada boot. Lê TABLES e adiciona o que falta: tabela, coluna, índice. Aditivo apenas — nunca remove nem altera.

2 · Migrations versionadas

src/lib/db/migrations/001..008

Para o que o sync não faz: transformar dados existentes, criar FTS5, dropar, renomear. Registro em migrations/index.ts, ordenado por version.

Ordem exata do boot — src/lib/db/migrate.ts:239

  1. Poda de backups antigos

    pruneOldBackups() — mantém os 3 mais recentes.

  2. Bootstrap de _meta

    Necessário para conseguir ler backupSchemaVersion.

  3. Detecta mudança de schema pendente

    storedSchemaVer < SCHEMA_VERSION e o banco não é novo → pendingSchemaChange = true.

  4. Backup ANTES de qualquer mutação

    backupDbLite(adapter, "schema-{de}-to-{para}"). Falha no backup é logada, não aborta.

  5. Aplica migrations pendentes

    Cada up() roda dentro de adapter.transaction — ou aplica inteira, ou nada.

  6. Sync declarativo

    Depois das migrations, para que uma migration possa criar a base que o sync depois completa.

  7. Estampa a versão alcançada

    setMetaSync("backupSchemaVersion", SCHEMA_VERSION) — o próximo boot pula o backup.

#NomeO que faz
001initialBase
002smart-routingTabela de perfis de modelo
003harness-conversationsSessões e eventos do chat

Por que o SCHEMA_VERSION foi para 8 mesmo sem mudança em TABLES. A migration 008 reescreve o blob onde as credenciais vivem. O bump existe só para forçar o backup pré-mudança a rodar antes disso — está comentado no próprio schema.ts:1-9. Esquecer o bump não quebra o sync aditivo; só pula o backup.

O modo de falha que a revisão desta semana fechou. A 008 lia data.testStatus direto do JSON.parse. Mas JSON.parse("null") tem sucesso e devolve null, então o try/catch de parse não pegava — ler uma propriedade de null lançava TypeError. Dentro da transação, isso dava rollback de todas as linhas e prendia a instalação em schemaVersion=7, falhando de novo a cada boot. Corrigido com guarda de não-objeto; tests/unit/connectionTestStatusMigration.test.ts protege a regressão.

Backup — src/lib/db/backup.ts

  • Dispara apenas antes de migrations de schema. Nenhuma rota de API o aciona.
  • Copia todas as tabelas exceto requestDetails (a maior e a menos crítica).
  • Destino: <DATA_DIR>/db/backups, os 3 mais recentes.
  • sai Fica local, nunca é transmitido — mas é SQLite em claro, com os tokens dentro.

SEÇÃO 06A primeira entrada de dados — instalação nova

Esta é a pergunta que você fez primeiro, e a resposta tem uma nuance que muda como se lê o resto do mapa: a criação do banco não é um passo de UI.

Cuidado com src/app/api/init/route.ts. O nome sugere bootstrap, mas o arquivo inteiro é:

export async function GET() { return new Response("Initialized", { status: 200 }) }

É um no-op. Nenhuma lógica de inicialização vive ali. Quem procurar o ponto de partida pelo nome da rota vai para o lugar errado.

O que realmente acontece, em ordem

  1. Processo sobe

    src/instrumentation.ts → register() chama initializeApp() e bootstrap(). Também instala a captura de console (initConsoleLogCapture()) que alimenta a tela Console Log.

  2. Banco nasce lazy, no primeiro acesso

    A primeira chamada a getAdapter() de qualquer lugar (driver.ts:92) dispara runMigrationOnce(). Tabelas, colunas e índices de TABLES passam a existir. Antes de qualquer tela abrir.

  3. /login — a porta

    A linha de settings é criada preguiçosamente a partir de DEFAULT_SETTINGS na primeira leitura. Vem com requireLogin: true, authMode: "password" e a senha padrão 123456 (src/lib/auth/dashboardSession.ts:8).

  4. /dashboard/providers/[id] — a primeira entrada de dados de verdade

    É a primeira tela onde o operador cria uma linha que ele controla. Adicionar uma chave de API ou concluir um OAuth insere em providerConnections. Nada a jusante funciona sem pelo menos uma linha aqui.

  5. /dashboard/endpoint — semeia sozinho

    endpoint/hooks/useApiKeys.ts:27-36 cria uma "Default Key" no momento em que a página carrega com zero chaves. Sem clique. Só visitar a tela já grava em apiKeys.

  6. Só então o resto ganha sentido

    Combos referenciam modelos que vêm das conexões. Usage e Quota ficam vazios até um request bater em /api/v1/*.

Um efeito colateral que vale saber: visitar /dashboard/endpoint ou /dashboard/basic-chat é uma escrita, não uma leitura. Ambos aplicam o mesmo padrão de auto-provisionar a primeira chave de API. Uma tela que grava ao renderizar não é o que se espera de uma tela de consulta.

SEÇÃO 11Seleção de conta, mutex e fallback

getProviderCredentials(), src/server/llm-gateway/auth/accountSelection.ts:119. É aqui que o dado criado no dashboard finalmente é usado.

O mutex — accountSelection.ts:17

A seleção muta a escrita do round-robin (lastUsedAt, consecutiveUseCount), então picks concorrentes do mesmo provider precisam serializar. O lock é uma cadeia de promises em Map<providerId, Promise<void>>, por provider — dois providers não têm estado compartilhado, e um lock global fazia todo request enfileirar atrás de um alheio.

O release() limpa a entrada do Map só se ela ainda for a sua (if (selectionLocks.get(providerId) === current)), então o Map não cresce por chamada. E o release inteiro está em finally (accountSelection.ts:288) — uma exceção no meio da seleção não deixa o provider travado para sempre.

O algoritmo, em ordem

  1. Provider noAuth? Curto-circuito

    FREE_PROVIDERS[id].noAuth → devolve credencial sintética { id: "noauth", accessToken: "public" }, opcionalmente com um proxy pool escolhido por pickProxyPoolId(). Nunca toca providerConnections.

  2. Carrega candidatas

    getProviderConnections({ provider, isActive: true }). Zero → devolve null.

  3. Filtra por exclusão e cooldown

    Fora as que estão em excludeConnectionIds e as que têm linha ativa em modelAvailability para este modelo (ou __all).

  4. Todas travadas? Reporta a que destrava primeiro

    Devolve { allRateLimited: true, retryAfter, retryAfterHuman, lastError, lastErrorCode } com o erro da conta de until mais próximo — não da que por acaso ficou primeira na lista.

  5. Escolhe pela estratégia

    preferredConnectionId fixa a sessão. Senão settings.providerStrategies[id].fallbackStrategy ou o global:

    round-robin — ordena por recência de lastUsedAt, mantém a mais recente por até stickyRoundRobinLimit (3) usos consecutivos, depois rotaciona para a mais antiga. Grava lastUsedAt e consecutiveUseCount.

    fill-first (default) — availableConnections[0], com priority || 999 como desempate entre contas nunca usadas.

  6. Resolve o proxy

    resolveConnectionProxyConfig(connection.providerSpecificData), e o resultado é anexado ao providerSpecificData devolvido.

Embeddings não gravam requestDetails. A rota /v1/embeddings chama saveRequestUsage() direto (embeddings.ts:181), sem passar por saveUsageStats, e nenhuma chamada a saveRequestDetail existe em embeddings.ts nem em engine/handlers/embeddingsCore.ts. Consequência concreta no produto: um embedding aparece nos totais de Usage mas nunca na aba de detalhes de request. Além disso o registro é condicionado a exactEmbeddingUsage(), que rejeita objetos de uso estimados — um provider que não devolve contagem exata não contabiliza nada.

Trace de roteamento — shared/observability/routingTrace.ts

Independente da persistência. Registra o que o gateway fez para responder: combo resolvido, decisão do smart routing, cada modelo tentado e por que falhou, e qual conta finalmente respondeu.

  • Viaja em um Symbol.for("routerx.routing.trace") no próprio corpo do request — toda camada de roteamento já recebe o mesmo objeto, então não precisa de storage por request nem de passar por doze assinaturas.
  • Sai no header X-ModelHub-Routing, anexado por withRoutingTraceHeader() reembrulhando a Response finalizada (inclusive corpos SSE).
  • Limites: 24 passos, 3.500 chars de header, 160 chars por erro. Estourar marca truncated: true em vez de perder o trace inteiro.
  • Cinco tipos de passo: combo, smart, adapter, attempt, account.

Este é o mecanismo que responde "por que essa resposta veio desse modelo?" sem precisar de enableObservability ligado — é o que a tela de Chat usa para mostrar a linha de decisão.

SEÇÃO 16Onde os dados não conectam

O objetivo declarado do mapa. Cada item foi verificado no código, ordenado por consequência real, não por gravidade teórica. Onde a resposta certa depende de uma decisão de produto, isso está dito em vez de escondido.

Alto · Segredos · verificado

Um segredo escrito no dashboard se espalha para quatro lugares sem cifragem

Adicionar uma credencial grava em providerConnections.data em texto plano. A partir daí, sem nenhuma ação extra do operador, o mesmo material pode chegar a:

(1) o backup pré-migration em <DATA_DIR>/db/backups, SQLite em claro, sem redação; (2) uma dúzia de arquivos de config de CLI sob ~/, escritos por /api/cli-tools/*-settings com a chave de API embutida; (3) variáveis de ambiente em Render/Railway, com uma gatewayApiKey real, via /api/cloud/deployments; (4) usageHistory.apiKey, em claro, numa tabela sem poda.

Nenhum desses quatro está errado individualmente. O que o mapa mostra é que não existe um inventário de onde o segredo foi — então rotacionar uma chave não tem procedimento fechado. É a maior lacuna estrutural do sistema.

Alto · Decisão pendente · modelResolution.ts:107

isModelDisabled falha aberto e não alarma

catch { return false } por decisão explícita, documentada no próprio código. Uma intermitência de leitura torna modelos desabilitados chamáveis de novo, em silêncio, sem log e sem sinal na UI.

Está certo se "desabilitado" for preferência de UI. Está errado se for controle de custo ou de compliance. Essa definição não existe no repositório, e mudar para fail-closed sem ela troca um risco silencioso por uma indisponibilidade. Requer decisão sua, não uma correção técnica.

Médio · Consistência de dados · verificado

Embeddings aparecem nos totais mas nunca nos detalhes

/v1/embeddings chama saveRequestUsage() direto (embeddings.ts:181) e nunca saveRequestDetail() — a chamada não existe em embeddings.ts nem em embeddingsCore.ts.

Efeito visível: um embedding entra em usageHistory e no gráfico de Usage, mas a aba de detalhes de request nunca o mostra. Quem for depurar um embedding não acha o registro e conclui que a chamada não aconteceu.

Agrava: o registro é condicionado a exactEmbeddingUsage(), que rejeita uso estimado. Um provider que não devolve contagem exata não contabiliza nada — nem custo, nem tokens.

Médio · Durabilidade · verificado

O cooldown do caminho de último recurso vive só em memória

Dois mecanismos de cooldown coexistem e não se falam. Providers com credencial usam modelAvailability — durável, por (conta × modelo), visível na UI. Providers noAuth usam noAuthCooldowns, um Map de processo, por provider inteiro (application/noAuthCooldown.ts:12).

O Map se perde a cada restart e não aparece em tela nenhuma. E como o fallback grátis (oc/big-pickle) é justamente um provider noAuth, o cooldown do caminho de último recurso é o mais frágil dos dois — exatamente onde se quer o comportamento mais previsível.

Médio · Limite arquitetural · auth/accountSelection.ts

O host seam não é exaustivo como a documentação afirma

ARCHITECTURE.md diz que o engine é isolado do host por engine/host/*, e tests/unit/hostSeam.test.ts prova isso para o que está sob engine/.

Mas accountSelection.ts — o módulo central de seleção de conta, mutex e fallback — importa connectionsRepo, proxyPoolsRepo, apiKeysRepo, modelAvailabilityRepo e settingsRepo direto. Ele vive em llm-gateway/auth/, não em engine/, então está tecnicamente fora do limite — mas é código de caminho quente que toca cinco repos sem passar pelo seam.

Não é um bug. É uma discrepância entre o que a arquitetura documentada promete e onde a fronteira realmente está. Quem confiar na frase "tudo que o gateway toca está em host/" vai subestimar a superfície em cinco repos.

Médio · Integridade referencial · verificado

Zero FOREIGN KEY no schema, com foreign_keys = ON ligado

O PRAGMA está ativo mas não há nenhuma FK declarada em schema.ts. Todas as relações — connectionId, skillId, sessionId, toolId — são convenção de código.

Caso concreto verificado: deleteProviderConnection() (connectionsRepo.ts:280) apaga só de providerConnections e reordena prioridades. As linhas de modelAvailability daquele connectionId ficam. A limpeza periódica (cleanupExpiredModelAvailability, chamada por /api/models/availability e backgroundTokenRefresh.ts:149) só remove linhas com until vencido — uma órfã com until IS NULL fica para sempre.

Não corrompe comportamento: as leituras filtram por connectionId IN (...), então órfãs nunca são lidas. É crescimento de armazenamento, não erro de resultado. Mas é o padrão que se repete: nada no banco impede o órfão, e o cleanup existente não cobre esse caso.

Médio · Governança inconsistente · verificado

Skills escapam da fila de aprovação; memória e plugins não

harnessPendingWrites gera exatamente dois tipos: kind:"memory" (quando a config exige aprovação) e kind:"plugin" (sempre, quando iniciado pelo agente).

create_skill, update_skill, patch_skill e learn_skill escrevem em agentSkills e agentSkillFiles direto, sem gate nenhum. E skills entram no system prompt das execuções seguintes.

Ou seja: o agente não pode ligar um plugin sem sua aprovação, mas pode escrever instrução persistente que ele mesmo vai ler depois. O modelo de governança está aplicado a dois dos três caminhos de escrita persistente.

O que foi verificado e está correto

Sem path traversal no Translator

/api/translator/load usa allowlist estrita de 8 nomes de arquivo antes do path.join. O parâmetro ?file= não é explorável.

Headers sanitizados na observabilidade

requestDetailsRepo remove authorization, x-api-key, cookie, token, api-key antes de gravar.

Settings à prova de concorrência

updateSettings() faz read-merge-write dentro de transação. Essencial, já que quase toda tela grava no mesmo blob único.

Mutex sem vazamento

Nenhuma telemetria

Deploy de proxy pool sem segredo

O worker de relay publicado é genérico. Nenhum segredo do ModelHub vai no código — ao contrário do caminho de cloud deployments.

Veredito sobre a pergunta que motivou o mapa. O caminho principal — dashboard grava credencial → gateway seleciona conta → traduz → executa → contabiliza — está conectado corretamente e é rastreável de ponta a ponta. O trace de roteamento fecha o ciclo: dá para provar, por request, qual conta respondeu e por quê.

As desconexões reais são de três tipos, e nenhuma está no caminho principal: (1) caminhos secundários que não recebem o mesmo tratamento do principal — embeddings sem requestDetails, TTS do Gemini com pipeline próprio, cooldown noAuth só em memória; (2) ausência de constraint no banco, com a integridade dependendo inteiramente da disciplina dos repos; (3) segredos sem inventário — o dado conecta, e é justamente por isso que ele chega a quatro lugares sem cifragem.
